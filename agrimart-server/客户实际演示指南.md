# 农惠达 AgriMart 客户实际演示指南

适用工程：`agrimart-server`。编写日期：2026-11-10。

本文供项目负责人、售前或开发人员在客户会议中使用，提供准备步骤、操作命令、预期结果和讲解话术。内容依据当前工程源码整理；演示前仍须在实际使用的电脑上完成一次全流程预演。

## 1. 本次向客户展示什么

建议用 15～20 分钟，围绕一个场景展开：**供货方录入农资，农户登录后查看商品、采购两件，系统计算金额并扣减库存，随后查询或取消订单。**

开场可以这样说：

> “农惠达面向农资采购场景。这次展示当前后端已实现的商品录入、账户登录和订单处理能力，我们用一笔采购单说明系统如何保存商品、计算应付金额并记录库存变化。支付接入和完整商家运营流程会单独说明当前进度。”

本次以 **API 工具或终端作为操作界面**。可以将下面的请求提前放进 Postman、Apifox，也可以直接使用 Bash 和 curl；客户重点观看商品名称、金额、库存和订单状态。

| 环节 | 当前可展示的行为 | 讲解边界 |
| --- | --- | --- |
| 注册与登录 | 注册默认农户账户，登录取得会话令牌 | 没有预置账号；令牌有效期为 7200 秒 |
| 商品录入与查询 | 保存名称、单价、库存，查询在售商品 | 商品发布尚未接通商家资格校验，不能据此证明商家权限完整 |
| 单商家结算 | 按服务端商品单价计算金额，下单扣减库存 | 当前只支持单商家订单，不展示自动拆单 |
| 订单查询与取消 | 买家查询本人订单，取消待支付订单 | 取消当前只改变订单状态，尚未恢复库存 |
| 支付 | 说明支付服务已独立，演示未配置供应商的服务级响应 | 未接入真实支付或沙箱，不展示收款成功 |
| 架构 | 网关、三个业务服务、三个独立逻辑数据库 | Nacos、完整退款、农机共享等属于后续工作 |

### 前端与旧原型的使用说明

仓库同级的 `../agriapp` 是旧前端，`../agridemo` 是旧后端原型。旧前端按成功码 `code=0` 处理响应，当前工程成功码为 `200`；登录数据结构、结算路径等也存在差异。**仅启动旧前端并将地址指向本工程，不能得到可用的完整页面演示。**

客户需要看页面时，可播放提前录制并标注版本的原型视频，或在独立环节展示旧原型；明确其对应工程与能力范围。页面与当前三服务的真实联调，应在契约适配并预演通过后安排。旧原型和当前网关默认都占用 `8080`，不能按默认端口同时启动。

## 2. 演示前一天：准备运行环境

### 2.1 工具与端口

准备 JDK 25、Maven、可正常运行的 Docker Compose，以及 `curl`、`jq`。下文命令使用 Bash，工作目录均为 `agrimart-server`。如果使用 Windows，请在可运行这些工具的 Bash 环境中操作。

| 进程 | 默认地址或端口 | 用途 |
| --- | --- | --- |
| MySQL 8.4 | `localhost:3307` | 保存三个服务的数据 |
| 用户服务 | `http://localhost:8081` | 注册、登录和会话 |
| 交易服务 | `http://localhost:8082` | 商品、库存和订单 |
| 支付服务 | `http://localhost:8083` | 支付接口 |
| 网关 | `http://localhost:8080` | 客户端统一 API 入口 |

先检查版本和 Docker 状态：

```bash
java -version
mvn -version
docker compose version
docker info
curl --version
jq --version
```

确认端口未被旧原型等进程占用。命令使用本地默认配置；如果已配置数据库或服务地址环境变量，先核对它们是否对应本次演示环境。

### 2.2 启动数据库并构建

```bash
docker compose up -d --wait
docker compose ps
mvn clean verify
```

预期：MySQL 显示健康，Maven 输出 `BUILD SUCCESS`，四个可执行 JAR 生成在各模块的 `target` 目录。

Compose 首次初始化数据卷时会创建 `agrimart_user`、`agrimart_trade`、`agrimart_payment` 三个数据库及对应账号；三个应用启动时各自执行 Flyway 迁移。已有数据卷不会重新执行初始化脚本。数据库账号缺失或使用旧库时，按 [后端 README 的开发数据库说明](./README.md#开发数据库)处理，不在客户现场临时重置数据库。

**已有验证的限制：** README 记录过 Docker Desktop 无法启动，三服务连接真实 MySQL、Flyway 实际执行和数据库账号隔离尚未完成端到端验收。因此，测试通过不能替代本机全流程预演；本指南也不代表已经完成现场环境验收。

### 2.3 分别启动四个应用

打开四个终端，每个终端先进入 `agrimart-server`，分别执行一条命令并保留日志：

```bash
java -jar agrimart-user-service/target/agrimart-user-service-0.1.0-SNAPSHOT.jar
```

```bash
java -jar agrimart-trade-service/target/agrimart-trade-service-0.1.0-SNAPSHOT.jar
```

```bash
java -jar agrimart-payment-service/target/agrimart-payment-service-0.1.0-SNAPSHOT.jar
```

```bash
java -jar agrimart-gateway/target/agrimart-gateway-0.1.0-SNAPSHOT.jar
```

确认每个应用均出现启动成功日志，没有数据库连接、迁移或结构校验错误。支付服务保持默认的 `PAYMENT_PROVIDER_CONFIGURED=false`；将开关改成 `true` 只会启用当前本地支付记录逻辑，并不等于接入了支付供应商。

另开一个终端，检查基础连通性：

```bash
curl -fsS http://localhost:8080/actuator/health | jq .
curl -fsS http://localhost:8081/users/health | jq .
curl -fsS http://localhost:8082/products | jq .
```

网关应返回 `{"status":"UP"}`，用户和商品接口应返回成功码 `200`。这里只是基础检查；网关健康接口仅报告自身状态，不会检查全部下游服务。支付服务通过第 5 节的请求另行确认。

## 3. 演示前 30 分钟：准备数据和展示窗口

使用一个供货演示账号和一个农户演示账号，避免供货与采购使用同一个身份。当前注册接口会将两个账号都设置为 `FARMER`；“供货演示账号”仅表示本次操作分工，不表示完成了商家入驻或角色审批。

准备以下虚构业务数据：

| 数据 | 本次使用值 |
| --- | --- |
| 商品 | 演示专用复合肥（50kg/袋） |
| 单价 | 128.00 元 |
| 初始库存 | 100 袋 |
| 采购数量 | 2 袋 |
| 订单金额 | 256.00 元 |
| 下单后库存 | 98 袋 |

提前打开本指南、API 工具或终端、[项目架构图](./项目架构.excalidraw)，将终端字体调大。保留一份成功预演的截图或录像作为故障备用，并标注录制日期和工程版本。注册、登录、建商品等准备工作尽量在客户到场前完成；正式演示从查看商品开始即可。

### 3.1 在同一个 Bash 终端初始化演示变量

第 3～5 节使用同一个终端，避免丢失令牌和商品、订单 ID。每次完整重演从这里重新开始，会生成新账号和新商品，不清除旧数据。电话号码仅作本地测试占位，不用于联系或发送短信。

```bash
export DEMO_API='http://localhost:8080/api'
DEMO_RUN="$(date +%s)"
DEMO_DIGITS="${DEMO_RUN: -8}"
DEMO_SUPPLIER="supplier_${DEMO_RUN}"
DEMO_BUYER="buyer_${DEMO_RUN}"
DEMO_PASSWORD='DemoOnly_2026!'
```

### 3.2 创建两个演示账号

```bash
curl -fsS "$DEMO_API/users/register" \
  -H 'Content-Type: application/json' \
  --data "$(jq -n \
    --arg u "$DEMO_SUPPLIER" --arg p "$DEMO_PASSWORD" \
    --arg phone "198${DEMO_DIGITS}" \
    '{username:$u,password:$p,realName:"供货演示账号",phone:$phone,email:"supplier@example.com"}')" \
  | jq .

curl -fsS "$DEMO_API/users/register" \
  -H 'Content-Type: application/json' \
  --data "$(jq -n \
    --arg u "$DEMO_BUYER" --arg p "$DEMO_PASSWORD" \
    --arg phone "199${DEMO_DIGITS}" \
    '{username:$u,password:$p,realName:"农户演示账号",phone:$phone,email:"buyer@example.com"}')" \
  | jq .
```

预期：两次响应均为 `code: 200`，返回不同的用户 `id`，角色为 `FARMER`。用户名或手机号冲突时重新生成演示变量，或使用已知凭据登录已有演示账号。

### 3.3 登录并保留两个身份的令牌

```bash
DEMO_SUPPLIER_LOGIN="$(curl -fsS "$DEMO_API/users/login" \
  -H 'Content-Type: application/json' \
  --data "$(jq -n --arg u "$DEMO_SUPPLIER" --arg p "$DEMO_PASSWORD" \
    '{username:$u,password:$p}')")"
DEMO_SUPPLIER_TOKEN="$(jq -er '.data.accessToken' <<< "$DEMO_SUPPLIER_LOGIN")"
DEMO_SUPPLIER_ID="$(jq -er '.data.user.id' <<< "$DEMO_SUPPLIER_LOGIN")"

DEMO_BUYER_LOGIN="$(curl -fsS "$DEMO_API/users/login" \
  -H 'Content-Type: application/json' \
  --data "$(jq -n --arg u "$DEMO_BUYER" --arg p "$DEMO_PASSWORD" \
    '{username:$u,password:$p}')")"
DEMO_BUYER_TOKEN="$(jq -er '.data.accessToken' <<< "$DEMO_BUYER_LOGIN")"
DEMO_BUYER_ID="$(jq -er '.data.user.id' <<< "$DEMO_BUYER_LOGIN")"

jq '.data | {tokenType,expiresIn,user}' <<< "$DEMO_BUYER_LOGIN"
```

预期：`tokenType` 为 `Bearer`，`expiresIn` 为 `7200`。展示账户资料即可；令牌留在变量或 API 工具环境中。后续请求如果失败或变量为空，先排查并重新登录，再继续执行。

### 3.4 录入演示商品

```bash
DEMO_PRODUCT="$(curl -fsS "$DEMO_API/products" \
  -H "Authorization: Bearer $DEMO_SUPPLIER_TOKEN" \
  -H 'Content-Type: application/json' \
  --data '{"name":"演示专用复合肥（50kg/袋）","price":"128.00","stock":100}')"
DEMO_PRODUCT_ID="$(jq -er '.data.id' <<< "$DEMO_PRODUCT")"
jq . <<< "$DEMO_PRODUCT"
```

预期：响应中 `merchantId` 等于 `DEMO_SUPPLIER_ID`，商品状态为 `ON_SALE`，库存为 `100`。价格按字符串传入，使用返回的真实 ID，避免假设商品编号为 `1`。

讲解话术：

> “这里保存商品名称、价格和库存。商品会关联录入账号，后续订单能够记录对应供货方。当前商家资格审核还需要补齐，本次先展示商品到订单的数据处理过程。”

## 4. 客户现场：按一笔采购单展开

建议节奏：开场 2 分钟，商品与账户 3 分钟，下单及库存 5 分钟，取消与支付说明 3 分钟，架构与交流 3～5 分钟。技术准备已经完成时，现场主要执行本节。

### 第一步：以农户身份查看商品

```bash
curl -fsS "$DEMO_API/products" \
  -H "Authorization: Bearer $DEMO_BUYER_TOKEN" \
  | jq --argjson id "$DEMO_PRODUCT_ID" '.data.records[] | select(.id == $id)'
```

客户应看到刚才录入的商品、`128.00` 元单价和 `100` 袋库存。商品查询现已支持游客访问，可省略 Authorization；列表使用分页，商品记录位于 data.records，默认每页 10 条。已有较多演示商品时，用 page 和 size 选择对应页。

讲解话术：

> “现在切换到采购方账号，看到的是服务端保存的在售商品。我们采购两袋，接下来同时观察订单金额和库存变化。”

### 第二步：采购两袋并创建订单

```bash
DEMO_ORDER="$(curl -fsS "$DEMO_API/checkouts" \
  -H "Authorization: Bearer $DEMO_BUYER_TOKEN" \
  -H 'Content-Type: application/json' \
  --data "$(jq -n --argjson id "$DEMO_PRODUCT_ID" \
    '{items:[{productId:$id,quantity:2}]}')")"
DEMO_ORDER_ID="$(jq -er '.data.id' <<< "$DEMO_ORDER")"
jq . <<< "$DEMO_ORDER"
```

预期：`code` 为 `200`，有 `id`、`orderNo`、`buyerId`、`merchantId`，`totalAmount` 数值为 `256.00`，状态为 `PENDING_PAYMENT`。JSON 可能将金额显示为 `256` 或 `256.0`，以数值相等为准。

讲解话术：

> “农户只提交商品编号和数量。系统从已保存的商品价格计算两袋共 256 元，并生成待支付订单，金额计算由后端完成。”

当前结算请求仅接收 `items`，不演示收货地址、运费或优惠券。不要反复点击或重发成功请求：当前流程没有展示防重复下单能力，重复请求会新建订单并再次扣库存。

### 第三步：回查订单与库存

```bash
curl -fsS "$DEMO_API/orders/$DEMO_ORDER_ID" \
  -H "Authorization: Bearer $DEMO_BUYER_TOKEN" | jq .

curl -fsS "$DEMO_API/products" \
  -H "Authorization: Bearer $DEMO_BUYER_TOKEN" \
  | jq --argjson id "$DEMO_PRODUCT_ID" '.data.records[] | select(.id == $id) | {id,name,stock}'
```

预期：可以再次查询到刚才的订单，商品库存从 `100` 变为 `98`。

讲解话术：

> “重新查询后，订单仍然存在，库存减少了两袋。这说明当前流程已经把采购结果写入后端，而不仅是页面上的临时变化。”

这一步证明本次串行采购的结果；并发采购、完整库存补偿和性能指标需要专项验证。

### 第四步：演示取消待支付订单

```bash
curl -fsS -X POST "$DEMO_API/orders/$DEMO_ORDER_ID/cancel" \
  -H "Authorization: Bearer $DEMO_BUYER_TOKEN" | jq .

curl -fsS "$DEMO_API/orders/$DEMO_ORDER_ID" \
  -H "Authorization: Bearer $DEMO_BUYER_TOKEN" | jq '.data | {id,orderNo,totalAmount,status}'
```

预期：订单状态为 `CANCELLED`。**当前取消逻辑尚未恢复库存，商品库存仍为 `98`。** 不向客户承诺取消后库存已补回；完整取消补偿应列入后续交付项。

讲解话术：

> “买家可以取消自己的待支付订单，并重新查询取消状态。当前已实现状态变更，库存返还还需要完善，正式业务验收时应把这两部分一起验证。”

## 5. 支付如何演示和解释

支付属于进度说明环节，不是成功交易闭环。当前供应商未配置，无法展示二维码、真实扣款、成功回调和到账。不要用内部支付事件接口或手工改库制造支付成功。

如果客户希望查看支付服务响应，先创建一笔新的待支付订单；不要沿用第 4 节已经取消的订单。

```bash
DEMO_PAYMENT_ORDER="$(curl -fsS "$DEMO_API/checkouts" \
  -H "Authorization: Bearer $DEMO_BUYER_TOKEN" \
  -H 'Content-Type: application/json' \
  --data "$(jq -n --argjson id "$DEMO_PRODUCT_ID" \
    '{items:[{productId:$id,quantity:1}]}')")"
DEMO_PAYMENT_ORDER_ID="$(jq -er '.data.id' <<< "$DEMO_PAYMENT_ORDER")"
```

以下为**开发人员本机直连支付服务的诊断操作**。使用网关内部身份头是为了观察服务本身的错误响应，不代表客户端应该自行设置身份；客户应用正常应通过网关传入 Bearer 令牌。若启动时设置过 `GATEWAY_TOKEN`，这里使用与支付服务一致的值。

```bash
curl -sS -i "http://localhost:8083/orders/$DEMO_PAYMENT_ORDER_ID/payments" \
  -H "X-Gateway-Token: ${GATEWAY_TOKEN:-dev-gateway-token}" \
  -H "X-User-Id: $DEMO_BUYER_ID" \
  -H 'Content-Type: application/json' \
  --data '{"amount":"128.00"}'
```

预期：HTTP `503`，响应的 `errorCode` 为 `PAYMENT_PROVIDER_NOT_CONFIGURED`。此处不使用 curl 的 `-f`，以便保留预期的错误响应正文。

讲解话术：

> “支付服务目前已独立出来，但还没有接入支付供应商，所以当前会拒绝发起支付。后续需要完成沙箱、可信订单金额校验、回调和退款协作，再进行付款成功的验收。”

这一步会让商品库存继续从 `98` 降为 `97`，并保留一笔待支付订单。当前支付创建逻辑尚未调用交易服务取得可信授权；示例中的金额字段不代表最终可上线的支付校验方案。

## 6. 演示前必须了解的已知限制

以下问题来自当前源码及已有测试，应在预演时核实。遇到对应情况，不将目标行为作为已实现结果讲给客户。

| 问题 | 对现场演示的影响 | 处理方式 |
| --- | --- | --- |
| 商品发布未接通商家资格检查 | 普通农户账号也可能发布商品 | 明确本次为录入流程演示，商家入驻、审批和发布权限待补齐 |
| 订单取消不恢复库存 | 取消后库存仍然减少 | 明确当前结果，后续补齐库存补偿 |
| 多商家结算尚不支持 | 多供货方商品一起结算会失败 | 本次只下单一个供货方的商品 |
| 旧前端与当前后端不兼容 | 页面可能将成功响应判为失败，或调用不存在的接口 | 当前工程以 API 演示；页面演示使用独立且已预演的版本 |

网关错误响应的空值异常、下游状态透传和用户 Bearer 转发已修复，并有回归测试。现场仍需按实际部署版本预演错误场景，不能将尚未实现的商家权限或资金闭环作为已验收功能。

## 7. 客户常见问题的话术

| 客户问题 | 建议回答 |
| --- | --- |
| 现在可以直接上线营业吗？ | “目前完成了部分基础交易能力。页面联调、商家权限、支付及库存补偿还需要完善，我们会按实际业务场景逐项验收。” |
| 能否在线支付并退款？ | “支付和退款属于下一阶段接入内容，本次展示供应商未配置时的真实结果。” |
| 可以一次采购多个商家的商品吗？ | “当前仅支持单商家结算，多商家拆单需要后续实现。” |
| 有没有物流、评价和农机租赁？ | “这些不在当前三服务的本次可演示范围，可结合业务优先级安排。” |
| 为什么拆成多个服务？ | “账户、交易和支付各自独立部署并保存自己的数据，便于按业务分工维护。当前可查看部署和数据库结构，跨服务协作仍有需要补齐的部分。” |
| 什么时间可以交付？ | “先确认页面、支付、商家管理等必需范围及验收条件，再根据实际开发和测试工作确定日期。” |

结束时记录客户最关心的采购角色、商品管理方式、支付方式和履约需求，将其转为可观察的验收条件，例如“取消待支付订单后，订单状态与可用库存同时恢复到预期值”。

## 8. 故障处理与现场备用方案

| 现象 | 优先检查 | 现场处理 |
| --- | --- | --- |
| MySQL 无法启动 | Docker 是否可用、`3307` 是否占用、`docker compose logs mysql` | 启动失败时改用已录制的预演材料，说明当前展示的是录像 |
| 业务服务启动失败 | 数据库地址和账号、Flyway 历史、Hibernate 校验错误 | 查看对应应用日志；使用预演时验证的配置 |
| 网关为 `UP`，业务请求失败 | 用户服务和目标业务服务是否启动、日志是否有网关错误响应异常 | 按服务定位；网关健康不等于全链路健康 |
| 登录后仍然失败 | 令牌是否为空或过期、是否仍在同一终端、请求头是否正确 | 重新登录，更新 API 工具或终端中的令牌 |
| 注册失败 | 用户名、手机号是否重复，密码是否不少于 8 位 | 使用新演示变量，或登录已创建的演示账号 |
| 库存或金额与示例不同 | 是否重发了结算请求、是否沿用旧商品 ID、是否执行了支付演示 | 从第 3 节创建新一轮数据，使用新返回的 ID |
| 旧前端出现“请求失败” | 是否连接了当前三服务、成功码和接口是否匹配 | 切回已准备的 API 演示或标注版本的原型录像 |

现场排查超过两分钟仍未恢复时，切换到准备好的截图或录像，继续讲解业务结果，会议后再处理环境问题。不要在客户现场清空数据库或修改迁移历史。

## 9. 演示结束后的处理

1. 保存本次使用的工程版本、账号名、商品 ID、订单 ID、成功截图和客户反馈；分享材料前隐藏令牌。
2. 演示数据保留在本地演示库中。重新演示优先创建新一轮数据；当前没有完整的数据清理接口，待支付订单也不能假定会自动关闭。
3. 四个应用分别在原启动终端按 `Ctrl+C` 停止；数据库可用下列命令停止，数据卷保留：

   ```bash
   docker compose stop
   ```

4. 本流程无需执行删除数据卷的命令。若需要彻底重建演示库，先确认数据用途并单独备份、安排清理。

## 10. 正式开始前的核对清单

- [ ] 在实际演示电脑上完成一次第 3～5 节预演，并保存真实结果。

- [ ] 供货、农户令牌均有效，使用各自身份进行发布和采购。
- [ ] 使用本轮新建商品，确认单价 128 元、初始库存 100、两件金额 256 元。
- [ ] 理解取消不返库存、支付未接入、商家权限待完善，并预演当前网关错误响应。
- [ ] 已准备好可读的请求、响应和架构图，说明页面原型与当前工程的区别。
- [ ] 已准备备用录像，并能明确区分实时操作和录制内容。
