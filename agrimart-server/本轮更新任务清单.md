# 农惠达 · 本轮三服务拆分任务清单

更新日期：2026-11-08。依据：根目录 `docs/` 的目标设计、现有 demo 源码，以及本轮确认的拆分范围。

**本轮第一次就拆成三个独立业务服务：用户管理、农资买卖、支付。先按大业务边界拆分，在各服务内部保留业务模块，后续按实际需要评估细分。** 统一网关、Nacos 和 MySQL 属于配套设施，不计入业务服务数量。

本轮交付是三个服务的首次拆分、数据隔离及必要的跨服务联调。先迁移 demo 已有能力，补齐独立运行必需的认证、支付记录与服务调用；`docs/` 中全部 54 个目标操作和所有后续业务功能不自动成为本轮任务。本次仅修订工作清单，没有实施代码拆分，下列事项均待执行与验收。

## 1. 项目前景与本轮取舍

项目近期围绕农资采购、商家履约和平台准入形成业务价值；后续可以复用身份和交易 API 建设 Flutter 客户端，再扩展农机共享。三个大服务分别承接身份、交易和资金责任，符合文档已经确定的边界。

商品、库存、订单、人工物流、评价及退款业务审核放在农资买卖服务内，可以保留交易内部的本地事务。支付服务负责资金事实，交易服务负责订单和库存，通过受保护接口协作。这样既能开始独立构建和部署，也能避免首次拆分就引入大量远程事务。

当前主要差距是认证、前后端契约、直接实体关联及支付能力。demo 没有可直接搬迁的独立支付模块，原有通用订单状态接口不能作为支付成功的可信依据。因此本轮包含既有代码迁移，也包含支付基础模块的新建。

商业价值仍需通过用户访谈和实际试用验证；早期调研中的行业数据、竞品判断不作为本轮排期依据。本轮先证明三服务边界成立、数据隔离、核心调用可验证，不承诺同时完成整个平台规划。

## 2. 本轮三个服务的明确边界

| 服务 | 工程与独立逻辑库 | 本轮迁移或新建内容 | 边界约束 |
| --- | --- | --- | --- |
| S01 用户管理 | `agrimart-user-service` / `agrimart_user` | 迁移用户模块；补齐可信会话、角色校验、内部令牌校验与商家资格查询 | 只维护用户、会话及经营资格，不管理商品、订单和支付记录 |
| S02 农资买卖 | `agrimart-trade-service` / `agrimart_trade` | 将商品、库存、订单、人工物流、评价整体迁入同一服务；接收支付结果并更新订单和库存 | 服务内部按模块组织；不继续拆商品、库存、订单、物流或评价服务，不直接调用支付通道 |
| S03 支付 | `agrimart-payment-service` / `agrimart_payment` | 新建支付记录、订单支付授权调用、支付发起与查询、可信结果处理及可靠回传 | 不审批退款业务，不直接修改订单、库存，不读取交易库 |

三个服务各有启动入口、配置、数据库账号、迁移脚本和测试。可共用一个 MySQL 实例，各自只能访问本服务库；跨服务不共享 JPA 实体、Repository、外键或事务。`agrimart-common` 仅放必要的基础协议与工具，是非运行模块。

| 本轮必须交付 | 后续单独安排 |
| --- | --- |

| demo 已有用户、商品、订单、物流与评价能力的迁移和必要修正 | 商家入驻审核完整页面、平台禁售等尚未实现的新功能 |

| 用户认证、商家资格查询、交易与支付的核心内部契约 | 文档中 54 个目标操作的全量落地 |
| 支付服务真实业务记录、授权、查询与结果归并；供应商接入状态如实记录 | 完整退款审批执行、迟到支付补偿及全部通道异常恢复场景 |

以上是本轮迭代切片，不修改 `docs/` 的阶段总目标。对暂未完成的目标行为必须标注限制，不能保留可绕过认证、支付或库存规则的旧接口来冒充完成。

## 3. 团队分工与交接

以下为责任分工，可一人兼任多个角色，不预设团队人数或承诺工期。服务代码可由团队成员分别推进；接口和数据约定需要先统一。

| 责任角色 | 本轮主要工作 | 向其他成员交付 |
| --- | --- | --- |
| 负责人／架构 | 冻结三服务边界、控制范围、协调契约与评审 | 迁移台账、接口范围、依赖顺序、验收标准 |
| 用户服务负责人 | 用户迁移、认证、角色与商家资格 | U01/U02、演示账号初始化、身份错误示例 |
| 农资买卖负责人 | 商品、库存、订单、物流和评价迁移 | 订单支付授权、结果接收、资源归属规则 |
| 支付服务负责人 | 支付基础模块、通道适配与可靠通知 | 支付记录、支付查询、通道状态说明和通知契约 |
| 前端负责人 | 请求、类型、会话和页面适配 | 经网关调用三服务的可演示流程与错误反馈 |
| 工程／测试负责人 | 版本、环境、数据迁移、构建部署及验证 | 可复现启动说明、隔离检查、联调与回退证据 |

认领时逐项填写：`任务编号 / 负责人 / 复核人 / 预计完成时间 / PR 或提交号 / 验证证据 / 阻塞项`。

## 4. 本轮执行清单

### A. 范围、契约与代码盘点

- [ ] **R01｜负责人**：确认本轮同时交付 S01、S02、S03 三个独立服务，冻结各服务职责与暂缓项；商品、库存、订单、物流、评价继续作为 S02 内部模块。
- [ ] **R02｜三服务负责人＋前端**：对现有 19 个接口及页面逐项登记目标服务、保留／替代方式、本轮行为和验收场景。特别标记旧 `GET /users/{id}`、携带用户 ID 的私有查询及通用订单状态写入口，防止遗漏替代或退役。
- [ ] **R03｜负责人＋测试**：区分“已有功能迁移、拆分必需新增、后续业务完善”，形成接口白名单；对跨商家结算等本轮未完成的复杂行为明确限制，不沿用混合商家订单冒充目标单商家订单。
- [ ] **R04｜三服务负责人**：先固定本轮跨服务 DTO、调用方、错误码、超时、幂等业务号及接口提供方；按现有 OpenAPI 契约裁定本轮子集，不另造一套临时协议，不要求一次实现全部 54 个操作。

### B. 工程、治理与数据隔离

- [ ] **R05｜工程＋后端**：依据实施时的官方资料验证并锁定 Java、Spring Boot、Spring Cloud Gateway、Nacos 客户端和服务端的兼容版本。现有 POM 声明 Java 25、Boot 4.1.1，不能据此假定新组合兼容。保留资料来源及验证结果。
- [ ] **R06｜工程＋三服务负责人**：在 `agrimart-server/` 建立 Maven 聚合工程、网关和三个服务，各自独立构建、启动与停止；需要时建立 common，但禁止放入共享业务实体或数据库访问代码。三个空壳或全部返回成功的占位接口不算拆分完成。
- [ ] **R07｜工程**：提供 MySQL、Nacos、网关与三服务的本地启动配置，验证注册、发现、配置加载和就绪状态。建议开发端口依次为网关 8080、S01 8081、S02 8082、S03 8083；与旧 demo 同时运行时另设旧端口。配置分环境，秘密不写入 Git 或日志。
- [ ] **R08｜工程＋三服务负责人**：建立 `agrimart_user`、`agrimart_trade`、`agrimart_payment` 三库及各自账号和版本化迁移脚本，验证跨库访问被拒绝。按本轮功能建必要表和唯一约束，暂缓功能的表可后续增加，不靠 `ddl-auto=update` 交付数据库变更。
- [ ] **R09｜用户＋农资买卖负责人**：实际解除 `Product.merchant`、`Order.user`、`Review.user` 及业务 Service 对 `UserRepository` 的跨服务依赖，改为逻辑 ID、必要快照和受保护接口；S02 内部的商品、订单、订单项等本地关联可以保留。
- [ ] **R10｜三服务负责人＋测试**：用虚构数据演练 demo 数据拆分，保留用户、商品、订单等 ID，校验密码摘要兼容、历史归属、订单项及评价关联。支付记录原本不存在，不给历史订单伪造通道交易；无法核实的旧支付状态标为历史演示数据，支付联调用新订单。保留旧库与可恢复备份，记录演练及回退步骤。

### C. S01 用户管理服务

- [ ] **R11｜用户负责人**：迁移用户模块，实现注册、登录、本人资料与退出；注册只能创建 `ACTIVE/FARMER`，数据库约束防止重复账号，错误凭据和无效账号被拒绝，不接受客户端自选管理员或商家角色。
- [ ] **R12｜用户负责人**：实现两小时有效、可撤销的不透明令牌，只保存摘要；校验过期、吊销和账号状态。其他服务根据可信身份检查角色和资源归属，不能用请求参数或浏览器保存的用户资料授权。
- [ ] **R13｜用户负责人＋调用方**：实现 U01 令牌校验及 U02 商家资格查询，供网关、S02、S03 按契约调用；内部服务凭据按调用方和接口授权。完整入驻审批流程未落地时，用离线初始化的虚构已批准商家联调，并保留明确的资格来源，不能把自助注册的角色当作批准依据。

### D. S02 农资买卖服务

- [ ] **R14｜农资买卖负责人**：整体迁移商品、库存、订单、人工物流与评价代码，保持模块内分层；补齐当前操作者、商家资格和资源归属校验。本人订单、商家商品及回复不能通过更换用户或商家 ID 越权操作。
- [ ] **R15｜农资买卖负责人**：调整下单与库存的本地事务，服务端核价、保存成交快照、预留库存，并对重复下单和并发扣减设置保护。每个可支付订单只属于一个商家；本轮若暂不实现多商家拆单，必须明确拒绝跨商家结算并同步标注与目标契约的差距。支付确认消费预留，未支付关闭后释放，副作用只执行一次。
- [ ] **R16｜农资买卖＋支付负责人**：实现 T01 订单支付授权与 T02 可信支付／关单事实接收；授权核对买家、金额、订单状态和期限。结果归并按业务号、事件号及版本去重，并在 S02 本地事务中更新订单、库存及流水；不能让 S03 直接写交易库。
- [ ] **R17｜农资买卖负责人**：用明确业务动作承接发货、收货与取消，退役通用“设置订单状态”入口。发货校验商家与状态，买家确认收货后直接完成；评价按本人已完成订单项校验并防重复。已发起支付的取消必须先完成查询及关闭确认，结果未知时保留 `CLOSING` 与预留库存，不因本轮功能有限而猜测取消成功。

### E. S03 支付服务

- [ ] **R18｜支付＋农资买卖负责人**：新建支付领域与持久化记录，以订单唯一约束复用稳定 `paymentNo`；通过 T01 获取可信金额、归属、币种与期限。实现支付发起和本人支付查询，S03 只访问支付库，不从客户端接受成交金额或付款成功结论。
- [ ] **R19｜支付负责人＋负责人**：评估并记录支付沙箱供应商的可用性，明确本轮是否接入。已接入时补齐创建、查询、关闭、验签及可信时间等适配协议；未接入时，真实发起返回 `503/PAYMENT_PROVIDER_NOT_CONFIGURED`，不能用按钮改状态或测试替身宣称真实支付成功。完整退款能力的实现范围另行列明。
- [ ] **R20｜支付负责人**：实现可信结果处理，以及供 S02 调用的 P01 支付关闭、P03 权威支付状态查询；只有验签成功的通知或服务端可信查询才可确认资金事实。校验金额、币种、环境及业务号，防止重复或乱序结果回退；未知结果保留明确状态。超期或已取消后收款不得复活订单，尚未完成的退款补偿标为功能阻塞，不能标记异常场景验收通过。
- [ ] **R21｜支付＋农资买卖负责人**：将支付事实与通知待办在 S03 本地事务内持久化，按原业务号重投 T02；S02 接收去重与本地副作用同事务提交。补充主动查询核对，验证响应丢失、S02 暂时不可用及进程重启不会丢结果或重复扣库存；不引入跨库事务。

### F. 网关与 Web 联调

- [ ] **R22｜工程＋三服务负责人**：统一 `/api` 网关入口，用户路由到 S01、交易路由到 S02、支付路由到 S03。`/orders/{id}/payments` 优先于通用订单路由；按契约处理前缀，阻断公网 `/internal/**`、`/api/internal/**` 和伪造身份头。S01 不可用时受保护请求不得放行。
- [ ] **R23｜前端＋三服务负责人**：同步请求封装、API 与类型，统一 `code=200`、真实 HTTP 错误、分页 `records/total/page/size/totalPages`、金额字符串、图片数组及评价字段。注册不自动登录，登录使用目标 `AuthVo`，刷新校验会话，退出吊销令牌；所有迁移页面通过网关访问新服务，不混用旧 demo 账号或令牌。
- [ ] **R24｜前端**：联调现有采购、订单、物流和评价页面，支付调用 S03 后查询可信结果；补齐加载、失败、空态与防重复提交。本轮沿用 Ant Design，不将全站 MUI 迁移捆绑进服务拆分；尚未实现的退款或其他操作明确禁用并说明状态，不能展示假成功。

### G. 验证、演示与交付

- [ ] **R25｜测试＋工程**：验证三服务分别构建、启停、注册发现、配置加载、数据库迁移与账号隔离；补充每个服务的业务测试，以及权限、重复请求、并发库存、通知丢失和依赖故障场景。仅加载 Spring 上下文或返回 HTTP 200 不算通过。
- [ ] **R26｜测试＋前后端**：用同一套虚构账号演示“登录 → 浏览商品 → 下单 → S03 创建记录并向 S02 申请授权 → 查询结果”。配置沙箱后继续验证“可信支付确认 → 发货 → 收货 → 订单项评价”；未接入沙箱时，只验收可验证的服务边界与内部调用，明确支付成功及其后续闭环未验收。测试适配器仅用于自动化测试，必须与真实沙箱配置隔离。
- [ ] **R27｜负责人＋工程**：提交实际可执行的构建、启动、初始化、联调及回退说明，附提交号和验证证据；按新工程执行后端测试，前端执行 lint、build。旧 demo 保留作对照和回退参考，迁移后的演示入口不再把核心业务交由它承接。逐项登记尚未实现、失败及未验证内容。

## 5. 执行顺序与交接门槛

| 顺序 | 推进内容 | 进入下一步前的交付 |
| --- | --- | --- |
| 1 | R01～R04：边界、现状、接口子集 | 三个服务的责任及相互调用契约已确定 |
| 2 | R05～R10：工程、治理、三库与数据解绑 | 三个服务能独立启动，数据隔离且虚构迁移数据可核对 |
| 3 | R11～R21：三块业务实现 | 团队成员按契约分别实现；先交付 U01/U02、T01/T02 供联调，测试替身不替代最终真实服务联调 |
| 4 | R22～R24：统一入口与 Web | 实际用户、交易、支付请求分别进入对应服务，前后端契约一致 |

这是同一轮内的实施顺序，三个服务均需在本轮落地，不按“本轮只做用户服务、以后再创建交易和支付服务”安排。

## 6. 本轮完成条件

- [ ] S01、S02、S03 均为真实可独立构建、启动和停止的应用；网关及 Nacos 作为基础设施配套运行。
- [ ] 原型已有的用户、商品、订单、物流和评价能力按本轮白名单迁入新服务；支付服务有真实记录、业务校验和跨服务调用，核心业务不依赖旧 demo 进程。
- [ ] 三库三账号及迁移脚本可验证，无跨服务实体关联、跨库查询、共享 Repository 或跨库事务。
- [ ] U01、U02、T01、T02、P01、P03 可在真实服务之间联调；退款相关的 T03/T04、P02/P04 等暂缓接口明确标为未实现。
- [ ] Web 通过同一网关调用三个服务，真实身份、资源归属及支付结果来源可追踪；旧通用状态写入口已退役。
- [ ] 重复通知、依赖短暂不可用和关键库存操作有验证证据；暂未完成的资金异常恢复列为功能阻塞，不以结构验收替代业务验收。
