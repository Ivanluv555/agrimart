# 项目结构与编码规范

本文件约定将要建设的三服务脚手架；当前 `agridemo/` 是待迁移原型，`agrimart-server/` 仍未实现下述工程。下述目录为目标规划，不表示工程已经创建。

## 1. 目标工程结构

```text
agrimart/
├── agriapp/                         # React + MUI Web 客户端
├── agrimart-mobile/                 # 后续 Flutter + Material 移动端，待创建
├── agridemo/                        # 现有原型，迁移期间保留
├── agrimart-server/                 # 目标 Maven 聚合工程
│   ├── agrimart-gateway/            # 基础设施：统一入口
│   ├── agrimart-user-service/       # S01 用户服务
│   ├── agrimart-trade-service/      # S02 农资买卖服务
│   ├── agrimart-payment-service/    # S03 支付服务
│   └── agrimart-common/             # 非运行模块：基础协议与工具
└── docs/                           # 业务边界及 01～09 设计交付物
```

`common` 不包含共享 JPA 实体、Repository 或可让多个服务访问同一库的代码。网关不是第四个业务微服务，Nacos 不承载商品、订单或支付业务。三个应用各自拥有配置、构建、启动、数据库账号、迁移脚本与测试；根工程只聚合依赖管理，不合并运行事务。

## 2. 技术与版本

Web 目标采用 React、TypeScript、MUI（Material UI）、Vite 与 Axios，现有 Ant Design 为待迁移原型依赖。后续移动端采用 Dart、Flutter 与 Flutter 的 Material 组件体系；移动端工程和依赖尚未建立。三个业务后端采用 Spring Boot、Spring MVC、Validation 与 Spring Data JPA；网关方向为 Spring Cloud Gateway，注册与配置中心方向为 Nacos。现有原型 POM 声明 Java 25、Spring Boot 4.1.1，不代表任意 Spring Cloud/Nacos 版本自动兼容。

脚手架实施前锁定并验证 Spring Boot、Spring Cloud Gateway、Nacos 客户端与服务端的兼容版本矩阵，验证发现、注册、配置及认证；不要从历史调研复制过时版本。开发起步阶段不强制增加消息队列、Redis、Seata、搜索引擎或独立文件服务。

## 3. 层次与领域

- Controller 负责路径、输入校验、身份提取和响应；Service 负责业务权限、状态机及本服务事务；Repository 只访问本服务数据库。
- S01 内按用户、认证、商家准入组织；S02 内按商品、库存、结算、订单、退款申请、履约、评价组织；S03 内按支付、通道适配、退款执行、通知与核对组织。
- 命名沿用 Java PascalCase 类名、camelCase 方法字段与小写包名，Java 4 空格、TypeScript 2 空格、UTF-8、LF；不把无关格式化混入功能提交。
- 输入用 DTO，输出用 VO，不将 Entity 跨服务序列化；远端用户、订单与资金关联只存逻辑 ID 或快照，不写跨服务 JPA 关联。

## 4. 跨服务与事务规范

- 每个服务只提交自己的本地事务。调用远端不持有数据库长锁；先提交状态和持久化待办，再投递命令或事件。
- 内部写命令按 commandId、事件按 eventId、支付按 paymentNo、退款按 refundNo 唯一；接收记录与本地副作用同事务提交。
- 使用状态前置条件和单调版本，阻止重复扣库存、重复退款与乱序回退。响应丢失时重放原业务号，不另建交易。
- 用户令牌由 S01 校验；内部服务凭据独立授权。网关拦截 /internal/**，服务端不信任客户端 X-User-Id 或角色头。
- S02 只维护支付/退款结果投影，S03 负责资金事实。失败保留 FAILED/UNKNOWN 或 CLOSING，不猜测成功；周期核对补偿丢失通知。

## 5. 数据、接口与前端

- 表按所属服务隔离，各库可使用本地外键；跨服务仅用 ID 逻辑引用，独立账号禁止跨库读写。
- 金额使用 BigDecimal，两位小数字符串传输，服务端核价；ID 不超过 JavaScript 安全整数范围。必填字符串规范化后校验，密码不裁剪。
- 统一 /api 网关入口和 code=200 成功体；失败使用真实 HTTP 状态及 errorCode。分页为 records/total/page/size/totalPages，1 起、每页最多 100。
- Web 与后续 Flutter 端分别封装网络请求、类型和错误处理，通过同一网关使用同等业务权限。本期 Web 购物车仅在内存中，后续移动端的本地状态与持久化需单独定义。
- 两端使用 Material 设计原则，统一主题色、字体层级、间距、交互反馈与可访问性要求。Web 使用 MUI 的 React 组件，Flutter 使用其对应的 Material 组件，不把 MUI React 代码直接用于 Dart 页面。
- 组件具备加载、空态、失败及防重复提交反馈；Web 验证键盘与焦点操作，移动端验证触控、文字缩放和设备适配。
- 接口变更必须同步修改客户端类型与实际调用，验证请求参数、响应模型、状态码和权限，不只修改接口示例。

## 6. 验证与提交

原型核对仍使用 agridemo 的 Maven Wrapper 和 agriapp 的 npm 脚本；三服务脚手架完成后，应分别构建测试三个服务、网关与各库迁移，再执行身份、库存、支付、退款及跨服务故障恢复验收。尚未生成工程时，不编造已可运行的命令。

纯文档变更检查链接、OpenAPI、图元素绑定、文字和连线布局即可，不必启动数据库或运行应用测试。业务变更覆盖权限、并发与故障恢复。保留无关已有修改，不提交构建产物、真实个人信息、私钥或环境秘密；VITE_ 变量是客户端公开配置。
