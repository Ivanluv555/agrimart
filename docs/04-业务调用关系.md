# 业务调用关系

本文件按业务步骤消费服务，遵循“上一步输出作为下一步输入”。以业务链明确调用方、提供方、关键输入输出、串行依赖和异常恢复。下文均为目标设计。

## 1. 通用调用约定

Web 客户端采用 React + MUI，后续移动客户端采用 Flutter + Material；两端复用相同的身份、业务权限和服务接口。外部访问先到网关。网关使用 U01 预校验令牌，服务端继续验证可信身份、角色及资源归属；内部调用使用调用方专用服务凭据，不接受用户直接访问内部接口。查询允许严格超时下的有限重试，写操作先持久化命令或事件再投递，重试复用相同业务号。

串行依赖必须等待上一步业务输出；同一页面中互不依赖的商品与评价查询可并行。支付受理、关闭受理、退款受理都不是资金完成证明。跨服务不共用事务：先提交本服务状态与待办，再调用远端，由通知或查询归并事实。

## C01 注册与登录

1. 客户端经网关调用 S01 注册，输入用户名、密码和本人资料，输出 ACTIVE/FARMER。
2. S01 登录校验密码及账号状态，输出不透明令牌、2 小时有效期与本人资料。
3. 后续网关及业务服务调用 U01，以令牌取得主体、角色与有效期；退出由 S01 吊销令牌。

失败：注册唯一性冲突返回 409；错误凭据返回 401；S01 不可用时受保护操作拒绝执行，不能信任本地伪造角色。

## C02 商家申请与审核

1. 农户向 S01 提交入驻申请，输出 PENDING 申请号。
2. 管理员将申请号和同意/拒绝决定传给 S01，申请与角色更新在用户库同一事务完成。
3. S02 发布、上架和下单时经 U02 获取 approved、active 与 shopName，不联查用户库。

失败：重复待审核申请、重复冲突决定返回 409；拒绝须说明原因；跨服务经营资格检查失败时不放行新的经营命令。资格校验是在交易提交前取得的可信快照，不是跨库锁。

## C03 浏览、购物车与结算拆单

1. 页面经网关向 S02 查询公开商品与评价，可并行加载；购物车暂存前端，不占库存。
2. 买家提交商品行及收货信息给 S02。S02 使用 U01/U02 检查主体及商家经营资格。
3. S02 在 agrimart_trade 本地事务内合并重复行、核价、按商家拆单、写商品快照和预留库存，输出 checkoutNo、各 orderId、金额与 expiresAt。
4. 客户端根据各 orderId 独立发起支付。任何商品无效、库存不足或自购，全部拆单与预留一起回滚。

## C04 独立订单沙箱支付

1. 客户端对一个 orderId 请求支付，网关将 `/orders/{id}/payments` 优先转给 S03。
2. S03 在支付库创建或复用按订单唯一的 paymentNo，再以 buyerId/paymentNo 调用 S02 T01。
3. T01 校验订单待支付、未超时及归属，将 paymentNo 绑定订单，输出 authorizationNo、金额、币种和到期时间。
4. S03 按该授权调用沙箱，返回 checkoutUrl；可信支付通知或主动查询确认成功后，S03 本地保存支付事实及 T02 通知任务。
5. T02 将 eventId、version、paymentNo、订单号、金额及支付时间交给 S02。S02 去重后在农资库更新 PAID、消费预留并增加销量，再确认接收。

Web 与后续移动端均可使用 checkoutUrl 打开沙箱结算页面，结果仍须服务端验签或查询确认，不默认存在原生支付 SDK 或深链接接入。

异常：供应商未选定或未配置返回 503；请求超时保留 INITIATING/UNKNOWN 并核对，不能新建第二个 paymentNo。S02 暂时不可用时 S03 重投事实，买家可见短暂未更新，但不得重复扣库存。

## C05 取消、到期关闭与迟到支付

1. S02 将待支付订单转为 CLOSING，并停止签发新的支付授权；若未绑定 paymentNo，可在本地直接取消并释放预留。
2. 已绑定支付时，S02 持久化 P01 命令。S03 设置关闭门闩，串行协调在途创建、通道查询与关闭，不能在关闭后再次创建可支付交易。
3. S03 通过 T02 回传 CLOSED 或 SUCCEEDED。确认未支付且关闭时，S02 本地取消并释放一次库存；有效期内已支付时转 PAID，取消不生效。
4. 超期付款或已取消后收款，S02 不复活订单，建立系统补偿退款和 P02 命令；后续按 C06 执行，但不需要商家审核，也不重复回补已释放库存。

异常：仅收到 202、查询超时，或创建调用仍在途时查不到交易，都不足以释放库存。P03 定期查询用于恢复丢失事实，按支付版本及同一归并规则处理。

## C06 申请、审核及执行全额退款

1. 买家向 S02 申请，S02 将 PAID 与退款申请 PENDING_REVIEW 同事务变为 REFUNDING，阻止发货。
2. 商家审核拒绝则本地恢复 PAID 并记录原因；同意则持久化审核决定和 P02 待办，不能立即标记资金已退。
3. S03 接到 P02 后用 T03 向 S02 获取不可变执行授权，核对自己保存的成功支付记录，按 refundNo 唯一建立资金执行记录。
4. S03 执行或查询通道，保存结果及 T04 通知。S02 接收去重后更新执行投影；成功时本地更新 REFUNDED、恢复库存并扣回销量。
5. FAILED/UNKNOWN 重试先查原退款，再复用同一 refundNo；P04 查询作为补偿，不能创建第二笔退款。系统迟到支付补偿的订单保持 CANCELLED，不再次改销量或恢复库存。

## C07 商家发货与买家收货

1. S02 校验所属商家、PAID 及无活动退款，保存承运方与运单号，转 SHIPPED。
2. 买家经 S02 确认收货，校验归属后转 COMPLETED。发货与退款申请竞争同一 PAID 前置状态，只允许一方成功。
3. 该流程均为农资服务本地业务，不调用支付服务改资金状态，不接物流公司轨迹接口。

## C08 订单项评价与商家回复

1. 买家向 S02 提交 orderItemId、评分及评价，S02 从订单项推导订单和商品，校验本人 COMPLETED 订单。
2. S02 以订单项唯一约束保存评价，在本服务内维护商品均分。
3. 所属商家向 S02 回复一次；公开列表只展示脱敏作者，不返回订单或收货资料。

## 2. 接口输入输出接力

| 调用 | 上一步输出 → 下一步输入 | 处理结果 |
| --- | --- | --- |
| 用户 → 农资/支付 | accessToken → U01 | 可信主体、角色及到期时间 |
| 用户 → 农资 | merchantId → U02 | 经营资格与店铺名 |
| 农资 → 支付 | orderId → 外部支付入口 | 创建稳定 paymentNo |
| 支付 → 农资 | paymentNo、buyerId、orderId → T01 | 授权、金额、币种、expiresAt |
| 支付 → 农资 | 持久化资金事实 → T02 | 本地订单与库存归并 |
| 农资 → 支付 | commandId、paymentNo → P01 | 只表示接受关闭，最终走 T02 |
| 农资 → 支付 → 农资 | refundNo → P02 → T03 | 已批准或系统补偿授权 |
| 支付 → 农资 | 持久化退款执行事实 → T04 | 本地退款投影和库存副作用 |
| 农资 → 支付 | paymentNo/refundNo → P03/P04 | 权威结果与版本，用于补偿核对 |

## 3. 为什么不引入跨库事务

用户审核和角色都在用户库，首次拆单和库存都在农资库，资金执行都在支付库。跨服务调用不持有数据库锁或跨库外键；通过可重放命令、去重收件、单调版本、状态前置条件和周期核对收敛。注册配置中心只解决发现和配置，不提供资金、订单或库存的业务原子性。
